# Модель угроз и правила аудита

## Защищаемые данные

Telegram auth key/session, локальная база TDLib, сообщения и вложения, контакты/метаданные, `api_id`/`api_hash`, настройки приватности, временные файлы и crash/log output.

## Угрозы и границы

- Вредоносный/повреждённый сетевой ответ и malformed TDLib JSON/update.
- Утечка сессии через логи, crash dump, backup, временный файл или permissions.
- Путь/имя файла из Telegram, symlink/path traversal, переполнение/диск exhaustion при загрузке.
- Ошибки обработки rich text, ссылок, документов, thumbnails и видео.
- Ошибки C ABI / строковых буферов / времени жизни указателей при FFI.
- Неконтролируемые очереди updates, media cache и UI history могут привести к DoS по памяти.
- Непреднамеренное нарушение Telegram API Terms, включая запрещённую модификацию read/online/typing state.

## Правила

- Не изобретать и не портировать самостоятельно криптографию Telegram. Передавать криптографические операции TDLib.
- Настоящие аккаунты/сессии никогда не входят в тесты, фикстуры, CI, screenshots или bug reports. Использовать synthetic fixtures и stub backend.
- `api_id`/`api_hash` читать только из config-файла с правами `0600`; не хранить в git, аргументах процессов или логах. Session database encryption key создавать через OS CSPRNG и сохранять в GNOME Secret Service; при недоступности keyring не продолжать без шифрования.
- Явный Logout выполняет TDLib `logOut` (удаляет локальные данные TDLib после сетевого завершения), затем bridge удаляет свой database key из Secret Service. Конфигурация приложения с `api_id`/`api_hash` не удаляется, поскольку это credentials приложения, а не пользовательская сессия.
- Каталог test/prod базы TDLib и файлы медиа размещать раздельно, закрыть доступ режимом `0700`. Не использовать реальные пользовательские данные в test DC.
- Устанавливать уровень логирования TDLib 0 и пустой log stream до инициализации instance. Не журналировать JSON запросы/ответы и сообщения.
- Любой `unsafe` остаётся в выделенном crate, с локальным `// SAFETY:` объяснением инвариантов, проверками длины/NUL/UTF-8, валидным ownership и отдельной ревизией.
- Ограничить размеры входов, очередей и кэшей. Обрабатывать ошибки без panic на границе сети/FFI.
- Не показывать remote content через shell/браузер без явного действия пользователя. Валидировать ссылки и пути, не доверять MIME/расширениям.
- Логи — только события и коды ошибок с редактированием идентификаторов; никакого текста сообщений/номеров/токенов.
- Проверять upstream security advisories и изменения Telegram API Terms перед релизом.

## Изолированные проверки

- Unit/property/fuzz tests для преобразования update JSON и типизированных событий.
- Boundary tests на выделенном mock C ABI, включая null pointer, некорректный UTF-8, oversized payload и порядок освобождения памяти.
- Storage tests во временном каталоге с синтетическими значениями, permissions и восстановлением после повреждённого файла.
- Media tests на traversal, symlink, имя файла, oversized declared size, частичную загрузку и cache eviction.
- Никакого живого сетевого аккаунта в автоматических тестах.

## Отчёт об уязвимости

Не публиковать рабочие сессионные данные и exploitable детали в открытом issue. Сначала определить затронутый компонент/версию, воспроизвести на synthetic fixture и подготовить минимальную безопасную запись с влиянием и исправлением.
